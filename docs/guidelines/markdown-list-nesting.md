# Markdown リスト項目のネスト規約

本リポジトリの skill が出力する markdown 成果物、および `docs/` / `AGENTS.md` / `README.md` などの内部ドキュメントで、**1 つの list 項目に複数の独立事実を `/` で連ねない → ネスト list に展開する** 運用ルールを SSOT として定める。

商談記録・提案書・調査レポート等のテンプレートで `- タスク — 担当: 田中 / 期日: 2026-07-20` のような書き方が発生していたが、これらは項目のラベルと値の対応が読み取りづらく、後で機械的にパースする際にも壊れやすい。ネスト list に展開することで人間の可読性と機械可読性の両方を保つ。

括弧の全角/半角ルールは対象外 ([`markdown-punctuation.md`](markdown-punctuation.md) 参照)。本ドキュメントで規定するのはリスト項目内の情報レイアウトのみ。

## 適用範囲

- `skills/**/references/*.md` の生成テンプレート、および skill が生成する markdown 成果物
- `docs/` 配下のドキュメント
- `AGENTS.md` / `README.md` / `HOW_TO_USE.md` 等のガバナンス系ドキュメント
- 対象外: GFM 表セル (`|...|`) 内の詰め込み、shell script 内のヒアドキュメント、コードブロック内、外部から取り込んだ引用 (原文表記を優先)

GFM 表セル内は行構造の制約からネスト list を挿入できないため本ガイドラインの対象外とする。表構造そのものの見直しが必要な場合は skill ごとに個別判断する。

## 基本原則

1 つの list 項目に **独立した事実** を 2 つ以上詰め込むときは、`/` 区切りの 1 行ではなくネスト list の子項目として分ける。事実が 1 つの場合はフラットな 1 行のままで良い。

- ❌ NG (独立事実を 1 行に詰め込み): `- タスク A — 担当: 田中 / 期日: 2026-07-20`
- ✅ GOOD (ネスト list に展開):
  ```markdown
  - タスク A
    - 担当: 田中
    - 期日: 2026-07-20
  ```
- ✅ GOOD (事実 1 つならフラットで良い): `- タスク A — 期日: 2026-07-20`

## 判定基準

「独立事実」「choice」「同種列挙」の 3 種類を切り分ける。

### 独立事実 (ネスト展開の対象)

複数のラベル/観点がそれぞれ独立した値を持つケース。ラベルと値のペアが 2 つ以上ある場合が典型。

- 「担当 / 期日」「金額感 / 予算取得状況」「氏名 / 役職 / 就任時期」など
- 「宛先: 会社名 / 部署 / 担当者名」のように 1 つのラベル配下で複数の属性を並べているケースも独立事実として扱う (ネスト list 展開の対象)

### choice (対象外)

同じスロットに入る **選択肢** を `/` で並べているケース。ネスト展開せず 1 行のままで良い。

- `{初回 / 提案 / 見積 / クロージング}` — フェーズの選択肢
- `{YYYY-MM-DD / 期日未定}` — 期日欄に入りうる値のバリエーション
- `{当たり / 外れ / 未検証}` — 判定結果の選択肢
- `{増資 / 減資}` — 事象の種別

判別のヒント: 「A / B / C のうちいずれか 1 つが最終的に採用される」なら choice。

### 同種列挙 (原則対象、例外あり)

同じ性質の値を複数並べているケース (取引先リスト、件数の内訳など)。

- 原則: ネスト list に展開する。人間の読みやすさが上がる
- 例外: **10 件以上の short-value 列挙で 1 行が明らかにコンパクトに収まる場合** はフラットな inline 列挙を許容する (例: `- タグ: alpha, beta, gamma, delta, ...` — この場合は `,` 区切りが自然でそもそも `/` を使わない)

判断に迷う場合はネスト展開を選ぶ (default ネスト展開)。

## 具体ルール

### ルール 1: 独立事実 2 個以上 → ネスト list

ラベルと値のペアが 2 つ以上ある list 項目は、必ずネスト list の子項目として分ける。

- ❌ NG: `- 提出者: <自社 会社名 / 担当者名>`
- ✅ GOOD:
  ```markdown
  - 提出者:
    - 会社名: <自社 会社名>
    - 担当者名: <担当者名>
  ```

### ルール 2: レコード型 template は子項目化

1 レコードあたり複数フィールド (氏名 / 役職 / 就任時期 / ソース URL 等) を持つ「記録項目」template は、フィールドごとに子項目に分ける。

- ❌ NG: `- 役員体制: 氏名 / 役職 / 就任時期 / 略歴ハイライト / ソース URL`
- ✅ GOOD:
  ```markdown
  - 役員体制
    - 氏名: {value}
    - 役職: {value}
    - 就任時期: {value}
    - 略歴ハイライト: {value}
    - ソース URL: {value}
  ```

### ルール 3: choice / 引用 / コードブロック内は原文保持

以下は `/` を含んでも書き換えない:

- choice の `{A / B / C}` (判定基準の「choice」参照)
- 引用ブロック (`>` プレフィックス) や外部ドキュメントからの直接引用
- コードブロック / インラインコード内の実データ・実コード表記
- path 区切り (`skills/<name>/references/<file>.md`) や date 表記 (`YYYY/MM/DD`)

### ルール 4: 事実 1 つの list 項目はフラットで良い

事実が 1 つしかない list 項目にわざわざネスト構造を導入する必要はない。無駄なネストは可読性を下げる。

- ✅ GOOD: `- タスク A — 期日: 2026-07-20`
- ❌ NG (過剰ネスト):
  ```markdown
  - タスク A
    - 期日: 2026-07-20
  ```

ただし、同じセクション内の他項目が複数事実を持つ場合は書式統一のためすべて子項目化しても良い (見た目の一貫性を優先)。

## セルフチェック手順

markdown template を新規作成・更新した際は以下を実施する:

1. 変更ファイルに対して `rg '\s/\s' path/to/file.md` を実行し、`/` 区切りの箇所を洗い出す
2. 各出現に対して判定基準 (独立事実 / choice / 同種列挙) を適用する
3. 独立事実 2 つ以上 (ルール 1) はネスト list に展開する
4. レコード型 template (ルール 2) はフィールドごとに子項目化する
5. choice / 引用 / コードブロック / path / date (ルール 3) は原文保持
6. 事実 1 つの項目 (ルール 4) はフラットのままで良い
