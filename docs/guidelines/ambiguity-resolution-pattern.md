# 曖昧さ解消のための質問 discipline パターン

## 概要

複数 skill が共通して持つ「曖昧な点があればユーザーに質問する」フェーズで、**質問の出し方** に統一的な discipline を適用するためのパターンを定義する。新規 skill を追加するとき・既存 skill の質問プロンプトを refine するときの参照点とする。

discipline は次の 3 規律で構成される:

1. **1 問ずつ問う** — 複数質問を束ねない
2. **各質問に推奨回答を必ず添える** — 白紙質問を user に投げない
3. **codebase で answerable な項目は問う前に grep / Read で潰す** — 「コードを読めば分かる質問」を user に投げない

## 背景

設計 md の起票・issue 化・実装計画といった skill には「曖昧な点があれば必ず質問する。曖昧なまま進めない」という共通フェーズが置かれることが多い。しかし **質問の出し方** を LLM 裁量に委ねると、次のような分散が起きる:

- 複数質問を束ねた長文プロンプトで user が回答を組み立てづらい
- 白紙質問(推奨回答なし)で user に認知負荷を丸投げ
- コードを読めば分かる質問を user に投げてしまい discipline の信頼を損なう

3 規律は、これらを封じるために質問フェーズを持つすべての skill へ inline 複製する共通 discipline として定義する。

## 規約

### 3 規律の本文(複製テキスト)

質問フェーズを持つ skill reference には次の文字列を inline で挿入する:

```markdown
質問の出し方は次の 3 規律に従う:

- **1 問ずつ問う**(複数質問を束ねない。依存順を見失う / user の回答組み立て負荷が上がる)
- **各質問に推奨回答を必ず添える**(user が同意 / 修正 / 却下を即答できる足場を作る。白紙質問は認知負荷を user に丸投げする)
- **codebase で answerable な項目は問う前に grep / Read で潰す**(user に「コードを読めば分かる質問」を投げない)
```

挿入時のインデントは挿入位置のリスト階層に合わせて調整する(本文中に列挙形式で組み込むときは 4 space インデント等)。

### 適用箇所の管理

**MUST**: 3 規律を inline 複製した箇所は、リポジトリ側で一覧を維持する (どの skill のどの Phase に挿入したか)。規律を refine するときに同期漏れが起きるため、複製箇所を追跡できない状態にしない。

挿入位置の慣例は、skill の Phase 内に「曖昧な点があれば質問する」相当の項目を置き、その直後に 3 規律ブロックを挿入する形。既存項目のサブ箇条として埋め込んでもよい (その場合インデントを揃える)。

### 規律 1 の許容例外: 同一曖昧点のバッチ集約

**1 回の実行で複数の対象 (親要素 + 子要素群など) を扱う skill** では、規律 1(1 問ずつ問う)に次の例外を許容する:

> **同一の曖昧点が複数の対象に共通する場合に限り**、バッチ単位で 1 問にまとめてよい

これは「複数の独立した曖昧さを 1 問に束ねない」という規律 1 の本質を侵さない。同じ質問を N 回繰り返すのは user の認知負荷を不当に上げるためであり、明示的なバッチ実行 context 下でのみ許容される。

逆に、**複数の異なる曖昧点を 1 問に束ねる** ことは引き続き規律 1 違反となる。例外条項は「同一質問の重複排除」のみを許容する。

## 設計上の不変条件

- **共有 reference 文書を作らない**: 3 規律を `docs/guidelines/` 等の共有文書に置き、各 skill から参照する形は採用しない。`gh skill install <owner>/<repo> <name>` で個別 skill が install されると repo-level の共有文書は配布されず参照切れになるため。**各 skill に inline で複製する** ことが配布上の必須要件となる
- **他 skill 名を本文に書かない**: AGENTS.md「単独で動く skill は本文に他 skill 名を書かない」原則に従い、3 規律の出典として特定 skill 名を本文に含めない。3 規律はそれ自体で完結した discipline として記述する
- **重複の容認**: 複数箇所への inline 複製を許容する。規律 core が安定しているため maintenance コストは低い。規律を refine する場合は本ガイドラインと全複製箇所を同期更新する
- **既存設計と衝突する skill には適用しない**: 既存設計が規律と衝突する場合は無理に適用しない。設計意図を破壊するよりも例外として記録するほうが健全

## 拡張ガイド

### 新規 skill に質問フェーズを追加するとき

質問フェーズを持つ新規 skill を作るときは、本ガイドラインの「3 規律の本文」をそのまま reference に inline 複製し、複製箇所の一覧に 1 行追加する。

### 規律を refine するとき

3 規律の文言を変更する場合は次の順序で同期する:

1. 本ガイドラインの「3 規律の本文」を更新
2. 複製箇所一覧に挙がっている全ファイルの該当ブロックを更新
3. 3 規律を Iron Law として持つ discipline skill がある場合は、その `why` 節も同期する必要があるか確認
