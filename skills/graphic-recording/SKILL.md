# グラフィックレコーディング画像生成

会議メモ・記事・仕様書などの内容を読み解き、印刷して配れる 1 枚のグラフィックレコーディング画像を作る。

以下で `$SKILL_DIR` は、この SKILL.md が置かれているディレクトリの絶対パスを指す。

## Phase 0: 画像生成能力のゲート

この skill の成果物は画像ファイルそのものであり、HTML・SVG・Mermaid・ASCII art・文章による構成案は成果物として認めない。代替物を渡すと「グラレコ画像が手に入った」という期待を裏切り、印刷用途にも使えないため、能力が無い環境では **何も作らずに止める** ことが正しい振る舞いになる。

まず、自分が実際に呼び出せる **画像を新規生成してファイルに保存できるツール** を 1 つ特定し、その名前をユーザーに伝えてから次のフェーズへ進む。

次のいずれかに当てはまる場合は、以降のフェーズへ進まずに停止する。

- 画像を新規生成できるツールが自分のツール一覧に無い
- ツールはあるが、このホストでは実際に実行できない。認証切れ・権限拒否・機能無効を含む
- 画像を扱えないモデルで動いている

停止するときは、このホストまたはモデルでは画像を生成できないため skill を実行できないことを伝え、画像生成に対応したモデルまたはコーディングエージェントで実行し直すよう案内する。ユーザーから「画像でなくてよい」「HTML でよい」と返された場合も、それはこの skill の担当範囲外であることを伝え、別の手段へ切り替える。構成案だけを先に出すこともしない。

## Phase 1: オプションの解決

ユーザーの依頼から入力・トーン・向き・出力先を読み取り、次を実行して解決値を得る。

```sh
"$SKILL_DIR/scripts/parse-options.sh" [<入力テキストまたはファイルパス>...] [--tone <tone>] [--orientation <orientation>] [--output <path>]
```

出力の `--- STYLE ---` 以降がトーン別の画風指示、`--- LAYOUT ---` 以降が向き別のレイアウト指示で、どちらも Phase 3 のプロンプトへそのまま組み込む。

スクリプトの呼び出しが失敗したときは 3 通りに分けて扱う。

- スクリプトが見つからない。シェルが 127 で終了する場合は、skill の同梱ファイルが欠けていることを伝え、再インストールを案内して停止する
- `exit 64` を返した場合は、stderr の usage をそのまま示し、取り得る選択肢を伝えてユーザーの指定を確認してからやり直す
- 数秒経っても戻らない場合は中断する。このスクリプトはネットワークもサブプロセスも使わないため通常は起きない。渡した入力文字列を確認するよう案内して停止する

トーンの指定が無ければ `standard` を使う。ただし依頼文に社内報告・役員向け・提案書といった文脈があれば `business`、ワークショップやイベントの雰囲気を伝えたい文脈があれば `pop`、白黒印刷やコピー配布の前提が読み取れれば `mono` を提案する。提案に同意されたらそのトーンで、断られたら既定のまま、別のトーンを指定されたらその指定で Phase 1 をやり直す。

出力先の指定が無ければ、作業ディレクトリに内容を表す短い kebab-case のファイル名で保存する。

## Phase 2: 入力の構造化

入力ファイルがあれば読み込む。入力テキストと併用された場合は両方を材料にする。入力がまったく与えられていない場合だけ、何を題材にするかをユーザーに尋ねる。題材が示されたらそれを入力として続行し、中止されたらそこで終了し、別の依頼が示されたら新しい依頼として Phase 1 から始め直す。

読み取った内容から次を抽出する。グラフィックレコーディングは全体像を一目で掴ませるものなので、原文の網羅ではなく構造の抽出を優先する。

- タイトル。原文に無ければ内容から短く付ける
- 1 行のサマリー
- 主要ブロック 3〜6 個。各ブロックは短い見出しと 2〜4 個の要点で構成する
- ブロック間の関係。順序・因果・対比のいずれかに寄せる
- 強調したいキーワード数個
- 結論またはネクストアクション

1 枚に収まらない情報量のときは、結論、主要な論点、補足の順に優先して落とす。原文に無い事実・数値・固有名詞を補わない。

どれを主要ブロックに残すか判断が付かないときはユーザーに確認する。優先順位が示されたらそれに従い、任せると言われたら上記の優先順位で自分で決め、中止されたらそこで終了する。

## Phase 3: 生成プロンプトの組み立て

次のテンプレートを埋めて画像生成プロンプトを作る。文字は画像生成モデルが最も崩しやすい要素なので、描かせたい日本語文字列は要約せずそのまま列挙する。

```
日本語のグラフィックレコーディングを 1 枚の紙に描いたイラストを生成する。

# 用紙
向き: <landscape なら横長 / portrait なら縦長>
縦横比: <ASPECT_EXACT>。この比率を厳密に指定できない場合は <ASPECT_FALLBACK> を使う。
ピクセル指定が可能な場合: <PIXEL_WIDTH> x <PIXEL_HEIGHT>

# 画風
<--- STYLE --- の内容をそのまま貼る>

# レイアウト
<--- LAYOUT --- の内容をそのまま貼る>

# 描き込む文字
タイトル: 「<タイトル>」
サマリー: 「<1 行サマリー>」
ブロック 1 見出し: 「<見出し>」/ 要点: 「<要点>」「<要点>」
ブロック 2 見出し: 「<見出し>」/ 要点: 「<要点>」「<要点>」
...
結論: 「<結論またはネクストアクション>」

# 文字の描画ルール
上に挙げた日本語文字列を、一字一句そのまま正しい日本語として描く。
読めない疑似文字・崩れた漢字・英字への置き換え・意味のない文字列を描かない。
文字は背景と十分なコントラストを取り、印刷しても読めるサイズにする。
列挙していない文字を勝手に追加しない。

# 避けるもの
写真的な質感、透かし、ロゴ、UI のスクリーンショット、実在する人物や企業の再現。
```

画像生成ツールが縦横比やピクセル数のパラメータを持つ場合は、プロンプト内の記述だけに頼らず、そのパラメータにも同じ値を設定する。A4 に厳密一致しなくても、A4 比率に最も近い指定を選べていれば良い。

## Phase 4: 生成と保存

組み立てたプロンプトで画像を生成し、Phase 1 で決めたパスへ保存する。

生成が失敗したときは 3 通りに分けて扱う。

- ツールがエラーを返した場合は、原因が一時的なものか能力の不足かを見極める。レート制限や一時的な障害なら 1 回だけ再試行する。能力の不足・認証切れ・権限拒否であれば Phase 0 と同じ扱いで停止する
- 安全フィルタなどで生成が拒否された場合は、拒否の理由に当たる表現をプロンプトから外して 1 回だけ作り直す。それでも拒否されたら、拒否された事実をそのまま伝えて停止する
- 応答が返らないまま 3 分を超えた場合は中断する。1 回だけ、ブロック数と文字数を減らした軽いプロンプトで作り直す。それでも返らなければ、ハングした事実を伝えて停止する

いずれの停止でも、HTML・SVG・文章による代替物は作らない。

## Phase 5: 検証と報告

保存した画像を実際に開いて確認する。生成しただけで完了と報告しない。

- タイトル・見出し・結論の文字が判読でき、指定した日本語と一致しているか
- 崩れた文字や意味のない文字列が紛れていないか
- ブロック数とレイアウトが指示どおりか
- 縦横比が A4 比率に近いか

崩れが見つかったら、崩れた箇所の文字列を短くする、文字数を減らす、ブロック数を減らすといった調整を加えて 1 回だけ再生成する。それでも改善しない場合は、直った点と直らなかった点をそのまま報告し、日本語の描画に強い画像生成モデルで実行し直す選択肢を案内する。取り繕った説明をしない。

最後に、保存先パス、トーン、向き、実際の画像サイズ、確認して分かった弱点を短く伝える。
